Positioning / a dated desk review

What did the change actually satisfy?

Expectrail checks a change against requirements a person has approved, on recorded input routes. The installed verifier accepts only when the engine’s record and the visual observations both pass. It tells you whether those checks held. It won’t find every bug. Installed verification: integrated · diagnostic · Measured scope and limits.

Reviewed November 14, 2026. Expectrail source: 1c5bf2b (main, after #429). The comparison below is about what each product documents. We didn’t benchmark the products against each other, and their pages may have changed since.

Writing code is cheap now. Checking it isn’t.

Coding agents have made writing code almost free, so the slow part of shipping is now checking that the code works. An agent can make its own unit tests pass while the running software is broken. A character ends up drawn inside the floor, a texture never renders, or a feature gets switched off to quiet a failing check. Expectrail answers one question about a change like that, and shows its evidence: did the running software do what was approved?

Why one source of evidence is easy to fool

Telemetry alone. With vision off and only the engine’s position log checked, Expectrail caught 4 of 8 held-out bugs and accepted 3 of 7 deceptive fixes (runs 41003749744, 41003751876, 41230177124). Coordinates look normal when a coin texture is missing or a character is drawn behind scenery.

A model as the judge. Muse Code judging before-and-after screenshots accepted 2 of 7 deceptive fixes, including a patch that draws the robot inside the ground, and rejected 5 of 10 valid mutation repairs. Outside frontier models falsely rejected valid fixes 1 to 5 times in 24. A judge that turns down working code that often can’t be what decides whether a pull request merges.

Two sources of evidence, and plain code decides

Models have narrow jobs in Expectrail. SAM 3.1 and Muse Glimmer 30B look at frames, Muse Spark plans probes, Muse Wonder triages failures and Muse Code writes patches. None of them decides the verdict. Ordinary Python does, and when vision is missing or unsure the answer is needs-review. To accept, the engine’s own record and what vision saw have to agree, on the public routes and on private held-out ones: 8 of 8 held-out bugs caught, 0 of 7 deceptive fixes accepted and 8 of 8 valid fixes accepted. Godot verify path.

Why the evidence makes repair work

When a check catches a defect, its evidence is what a fixer needs. In run 41330361829, Muse Code repaired 10 of 10 caught random mutations on its first attempt. In Fix matrix run 41223754703, attempts given only a bug report timed out three times in a row on both sinking bugs; given Expectrail’s structured evidence (the check, the verdict and the first failing frame), Muse Code fixed each on the first attempt. Report first, verify always.

Because the verifier says exactly what failed, it can do more than block a pull request: it can hand that explanation to a fixer and get a patch back. The fixer runs in bubblewrap with no network of its own; its model calls go through the key gateway, which holds the real key. Repair is opt-in: it starts only after a reject with auto-fix turned on, works on a separate copy, and a fresh verification judges each candidate. The original reject stands, and a person reviews any accepted patch; Expectrail never merges a fix. Verify, then repair.

From games to web and mobile apps

Static webpages are out of scope: a DOM check already tells you what they show. Canvas-heavy web apps, mobile checkout flows and game engines share the same verification contract: replay a route, record what the runtime says it did, observe what was actually drawn, and let plain code decide. We started with games because constant physics, layering and sprites make them the hardest place to prove this works. The same verifier has been measured on one web checkout page, in Chromium desktop and phone browser sessions (run 41109233666: 8 of 8 development bugs caught with SAM on); canvas, WebGL and native mobile apps have not been run yet.

What an agent-run test result establishes

A passing test establishes the assertions that were exercised. Python’s test-framework documentation defines a test case in terms of particular inputs and expected responses. If an agent only runs logic assertions, the successful exit does not by itself show that the player was drawn visibly or above the floor. That is about a setup that only runs logic assertions; agents can run visual tests too. Python unittest documentation (reviewed November 14, 2026) · Expectrail’s measured visual-check scope.

Expectrail adds an explicit policy to that setup: routes and approved checks from a supplied base, declared windows and tolerances, and a combined engine/vision result. An engine pass without usable vision remains needs-review in the installed path. The ledger’s vision results are on seeded defects in one game; they don’t give a general catch rate. Policy and observer evidence · Vision measurements (ledger reviewed November 14, 2026).

An agent can invoke a verifier or build assertions that cover the same behavior. What matters is which checks and evidence the decision requires, not who pressed the button. That is our reading of how test frameworks work and of Expectrail’s own rule, and other tools can do the same. Test-framework semantics · Expectrail’s rule (reviewed November 14, 2026).

Public documentation: Ziva and nunu.ai

Both products describe observing a running game or app and checking outcomes. We have not installed or benchmarked either product. The following is a desk review of the linked first-party pages, accessed November 14, 2026; what a company writes about its product is its own claim, and we haven’t measured it.

Ziva

Ziva’s Create and test guide describes keyboard/mouse input, screenshots and error inspection. It documents a full playtest agent with pass, fail or blocked outcomes and optional video recording. Its Full game tester page describes reading code, pausing between actions, pursuing user-supplied goals and using hosted models. That page also says playtesting may temporarily change project files for diagnostics, while its comparison table says the playtest agent ships without write tools. We couldn’t tell from the pages which one is right. Sources accessed November 14, 2026; the Create and test page states it was updated that day.

nunu.ai

The agent introduction describes a screenshot/action loop with optional game state and SDK functions. Verification Tests documents ordered steps, explicit expected results, a time budget and per-check outcomes including skipped or blocked. Its Minion guide documents self-hosted Windows PCs and connected Android devices, with access enabled on request. So we don’t suggest nunu.ai lacks explicit checks, evidence review or self-hosting. Sources accessed November 14, 2026; Verification Tests states an October 1, 2026 update.

Expectrail’s limits belong in the comparison

The two-job Action merged in #429: candidate capture is separate from base-side judging with recorded vision. Its cited tests use stand-ins; this review adds no hosted acceptance demonstration. The bundled recording can lack answers for novel frames and combat, and clearance is advisory on Expectrail’s own repository. The earlier composite actions remain engine-only. The installed verifier’s current vision default has offline test evidence, while its cited live orchestrator run predates that default. No ledger row has isolated or protected grade. Action limits · Current verifier evidence (reviewed November 14, 2026).

The game originates its captured frames and trace, and the replay sandbox shares the host kernel. So Expectrail can’t rule out a malicious game faking its own evidence. Coverage is limited to the supplied checks and exercised routes. Capture boundary · Sandbox boundary · Coverage scope (reviewed November 14, 2026).

Use this review to decide what to evaluate: an existing regression with an observable requirement, a repeatable route and evidence you can inspect. Keep unit tests, exploratory playtesting and human judgment alongside it. That is how we’d suggest evaluating it. We’re not claiming it beats the alternatives.
