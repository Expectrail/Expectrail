Install the complete pair of jobs

  1. Put the pull request caller, reusable capture workflow and trusted publisher together on the default branch. The base checkout must contain Expectrail. The caller below is the current repository file, not a standalone installation: it needs both other files and their supporting code.
  2. Configure the same game folder, approved-spec directory and public routes in capture and judge. Review changes to either capture workflow separately: their paths and revisions are part of the publisher’s identity check. Do not put model keys or the publisher credential in candidate capture.
  3. Have the repository owner install a dedicated GitHub App with Checks read/write. Follow the canonical instructions for EXPECTRAIL_CHECKS_APP_ID, EXPECTRAIL_CHECKS_PRIVATE_KEY and the protected main-only environment, restricted to the default branch. On Expectrail itself the App ID is a repository variable and the private key is an environment secret. This guide does not configure those settings.
  4. Validate both jobs on a test pull request before requiring clearance: the trusted workflow must start, publish its report and attach the two checks to the current PR head. For a game repository, select Expectrail clearance with the dedicated App as its expected source. A same-named ordinary Actions job must not satisfy that rule. Keep ordinary tests and human review.

These setup requirements and the distinction between the two checks come from ci-gate.md; the ledger row separates the offline tests from deployment evidence still needed.

Self-hosted runners for private projects

Use a runner you administer when the project’s hardware or access policy requires it. The two-job ledger row has offline tests, not a deployed private-studio fleet. Treat the following as deployment guidance, not a measured private-project result. Recorded Action scope · Packaged platform limit.

  1. Prepare a disposable Linux machine. Start with the quickstart’s Python 3.12+, Godot 4.7.2, Xvfb, Mesa, patch, curl and unzip. Add bubblewrap and verify that the host permits the namespaces it needs. The reusable capture workflow installs system packages and enables replay namespaces with privileged host setup; it is not an unprivileged preinstalled-runner interface. Its current Python setup uses 3.13. Prerequisites · Sandbox requirements.
  2. Limit which jobs can reach it. Register it in a runner group restricted to the intended private repository. Use a dedicated disposable VM with no production credentials or access to unrelated projects. Rebuild it between untrusted jobs. GitHub warns that self-hosted runners can retain compromises between runs, including for private repositories. GitHub runner security guidance (reviewed November 14, 2026).
  3. Select your runner in your own workflow. The caller delegates to a reusable workflow: runner selection belongs in its capture job, not in the caller’s uses job. Review the trusted publisher’s runner separately. Never reuse a candidate-compromised host for trusted judging or publishing. Runner changes require separate review of the capture workflow identity. GitHub documents runner selection; this guide does not register a runner or change repository permissions.
  4. Require the sandbox and inspect the evidence. If capture cannot start the required sandbox, do not use an unsandboxed fallback; clearance must stay failed or incomplete. Check the recorded isolation and observer information. The split capture requires sandboxing and enables the necessary kernel settings; on a persistent runner those changes outlive the job. Plan it with the machine owner. This namespace sandbox shares the host kernel and has the resource limits listed in the ledger. Isolation evidence and limits.

Choose where private evidence may go

Self-hosting the replay does not make the workflow offline. Capture and the trusted judge upload artifacts to GitHub. The current judge reads recorded vision answers and makes no paid model call. If you separately use installed verification with hosted vision, it sends frames and prompts to its provider; those images may reveal unreleased art or UI. Review each destination before using private project data. The merged split separates judging from candidate execution; use separate disposable hosts so a persistent runner does not undo that boundary. Artifact and job boundaries · Hosted vision scope · Verifier key handling.

If policy forbids hosted inference, do not silently turn vision off and call the result an accept. Open-weight and bring-your-own vision paths have different evidence and limits, described below. No air-gapped deployment is established by these guides. Keep candidate execution free of model keys and production credentials. Open-weight limits · BYO vision: fixture only.

Model providers: choose by role

The two-job Action above uses a base-side recording, not the live provider settings below. Both paths need visual evidence for accept; recorded-answer coverage and paid-model availability are different limits. Action recording scope · Installed vision scope.

Vision is required for an accept from the installed verifier. Choosing a drafting or fixing model does not supply visual evidence. With the default vision path, MODEL_API_KEY and EXPECTRAIL_SAM_USD_CAP belong in the verifier’s environment. Missing either sends nothing: an engine failure can reject; otherwise the result needs review with PROVIDER_FAILED. This behavior is tested offline; the cited orchestrator live run predates the vision default. Current rule and evidence.

Configure only the role you mean to change

For optional drafting and triage, the repository router accepts EXPECTRAIL_SPEC_PROVIDER and EXPECTRAIL_TRIAGE_PROVIDER, with role-specific _MODEL, _API_BASE and _API_KEY settings. These override general EXPECTRAIL_LLM_* settings. Changing them does not select the visual observer. Check the router’s current provider/key mapping before configuring an endpoint. This is repository tooling, not a claim that drafting is bundled in the installed command. Router scope · Package scope.

Vision backends have their own EXPECTRAIL_VISION_BACKEND selector and endpoint credentials. The historical open-weight notes describe their measured setup. Do not transfer one backend’s accuracy, privacy or billing assumptions to another; read its row first. Glimmer limits · BYO vision limits.

Set a spending boundary before a live request

For default SAM vision, set EXPECTRAIL_SAM_USD_CAP to a finite, nonnegative US-dollar amount you choose. Missing or invalid is not unlimited. Zero permits no paid request; reaching the cap cannot turn an unanswered check into a pass. The reservation is checked before a request and counts retries at the client’s list-price estimate. It is a process/run limit, not an account-wide or monthly quota. SAM scope · Missing-setting behavior · Cap implementation.

The historical example in sam.md is up to $0.60 for both prompts over one 120-frame run. It is not a suggested cap or a quote for your project. Do not treat this setting as a spending cap for Glimmer deployments, optional language models or coding agents: BYO agent calls are unmetered by Expectrail, and the ledger reports no per-run fixer spend. Set the relevant provider’s own budget and usage controls separately. Vision cost scope · Agent metering limit · Provider spend limit · Fixer spend limit.

Keep verifier credentials separate from a fixer’s credentials and out of a candidate job, source files and logs. Use doctor to check settings without displaying the key and report to see which observers judged. A provider outage or exhausted cap is missing evidence, not permission to switch to engine-only acceptance. Doctor/report scope · Observer rule.
