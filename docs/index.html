Verification first · Verify the change · Keep the evidence

Coding agents write changes at machine speed. Expectrail proves they actually work—and, when you opt in, repairs what fails for a person to review.

Autonomous coding agents can make unit tests pass while breaking the running software: drawing a character inside the floor, hiding a checkout button behind a banner, failing to render a texture, or disabling a feature to silence a failing check.

Expectrail replays the changed software in a harness against approved and per-change checks, cross-examines internal runtime telemetry against external visual observation (SAM 3.1 or open-weight Muse Glimmer 30B), and uses plain deterministic code—never a model—to report accept, reject, or needs-review. When a check catches a defect and you turn auto-fix on, Expectrail gives the failing check’s words, route log and first failing frame to a sandboxed fixer agent on a separate copy. A fresh verification judges each candidate, and a person reviews any accepted patch.

01 / Structural Novelty

Why single-channel verification cannot govern autonomous agents

When an autonomous agent is tasked with fixing a bug, any verification gate that relies on a single channel can be gamed or hallucinated. We measured all three verification structures against the same 8 held-out bugs (across four families: physics-fall-through, missing-texture, layering, and sinking), 8 valid fixes, and 7 deceptive fixes that look plausible on the surface.

02 / Stress-Testing the Premise

How we broke Expectrail’s initial premise—and what it proved

Human-approved checks caught 8 of 8 seeded bugs and 31 of 39 targeted wrong fixes. We then designed a pre-registered mutation experiment specifically to break Expectrail: injecting 77 random single-edit mutations across the codebase.

Act I · Breaking static checks

The 0.9% random mutation catch rate

Across 77 random single-edit mutations (runs 41268023631, 41323827584, 41323829361), static human-written checks caught 10 of 77 raw—a 0.9% catch rate when weighted by how common each edit type is.

Why? 0 of 45 mutations that moved, resized, or re-layered objects were caught because 44 of them touched background scenery that no human had written a check to watch. Static checks only guard what someone thought to specify. Mutation bench.

Act II · The repair discovery

10 of 10 repaired when caught

What happened to the 10 random mutations our checks did catch? When Expectrail passed the catching check’s words and evidence to Muse Code (run 41330361829), Muse Code fixed 10 of 10 on the first attempt across all 6 routes (5 unseen by the judge).

Meanwhile, Muse judging those exact same 10 fixes from screenshots alone falsely rejected 5 of the 10 working repairs. This proved the bottleneck in autonomous software is not the coding model—it is check coverage and evidence quality. AI-written fixes bench.

Act III · Closing the blind spot

Advisory discovery and per-change checks

To address defects nobody wrote a human check for, we built Advisory Discovery (reading invariants from the game’s code + planning via Muse Spark) and Per-Change Generated Checks (synthesizing checks from the diff itself).

Result: caught 7 of 16 blind post-freeze defects (runs 41248745687, 41319184209, 41319197682), flagged 4 of 4 sabotage fixes that disabled features while ignoring 2 valid retunes (41326269491), found 4 of 4 reported Godot bugs (41238187197), and raised 0 of 4 false alarms on intentional design changes. 03 / Domain Generalization

Why we started with game engines—and how the same verifier carries to visual Web & Mobile

Most static webpages do not need Expectrail. Expectrail is built for stateful, visually complex software where unit tests and DOM selectors pass while the rendered user experience is broken. We started with a 2D game engine (and a 3D Unity harness) because continuous 60fps physics, z-index layering, and sprite rendering represent the hardest visual state machine in software—and we have already pointed the exact same verifier at a web checkout page.
