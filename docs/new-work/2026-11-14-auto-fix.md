# Opt in to repair after verify rejects a change (#433)

## What changed

A reject can start the existing repair loop when verify receives `--auto-fix`. The parent job keeps its reject and exit code. Its summary and evidence viewer show the independent repair outcome, the repair record and the winning patch’s review label. The local app exposes the same opt-in with an attempt limit and a dollar cap. A detached worker runs the same loop. A fixture or recorded patch runs offline. A live request needs an explicit dollar cap and the Muse meter.

## What was run

- `python3 -m unittest discover -s tests -t .` ran 3,280 tests before the change and 3,290 after it. Both runs ended OK with 42 skips. Neither had any failing or erroring test names.
- `python3 -m unittest -v tests.test_auto_fix` ran 10 tests, OK. The first five failed on the unchanged slice 1 base. The tests cover an accepted fix, exhausted attempts, a changed patch, a stopped worker, budget checks, the local app, and jobs that never start repair.
- The handover’s `observe.py` started detached worker processes with offline observers. The original job exited 1 for reject. One candidate was accepted and matched the fixture patch. The viewer link resolved to that job’s repair record.
- The handover’s `check_meter.py` checked the Muse cap against #436’s meter with zero requests. The app script passed `node --check`.

## Not done

No live fixer, paid observer or real game engine was run. The viewer was not looked at in a browser. This change covers the verify command and job viewer. CI automation is outside this handover.
