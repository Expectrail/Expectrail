Concepts / read the scope before the verdict

What did this result establish?

A verification result answers configured questions about a replay. Its evidence, routes and check windows bound that answer. It does not certify everything a game can do. Measured check scope.

ChecksRoutesDecisionsVisionGradesClearanceThreat model

Checks state the requirement. A person approves it.

A check describes the object, condition, tolerance and frame window to judge. A draft is a proposal, not permission to decide a change. The drafting path produces unapproved specs; a person reviews the wording, bindings and limits before approval. Spec-writer evidence and limits.

Verification does not approve a spec. With a base checkout, the job uses the base’s checks and routes and records their digest. Changing the candidate’s checks is not a substitute for satisfying that policy. Policy and input boundaries.

Generated and discovered checks remain advisory in their ledger rows; do not treat them as additional enforced coverage. Generated-check status · Discovery status.

A route is a reproducible input sequence, not exploration.

Routes name inputs and when to press or release them, with a seed and duration. The harness replays the route and captures frames and an engine trace. Its cited replay evidence is integrated, diagnostic evidence on the listed platform. Harness row.

A check can cover only its configured window on those routes. The measured verification row’s approved specs judge frames 0–119; do not infer coverage of a whole level, a different route or another project. Check-window limits.

Three decisions, with different meanings

DecisionRead it as
acceptThe configured checks passed with their required observations. The answer is bounded by the checks and routes.
rejectA check failed. An engine failure can reject even when vision did not answer.
needs-reviewThere is not enough usable evidence to accept: for example, missing vision settings or no approved checks. This is not a pass.

Decision rule and tested cases

A failed, cancelled or unfinished job is not a completed accept. Doctor and sample also have their own exit meanings; follow the quickstart’s expected results rather than assuming every nonzero exit means a behavior failure. Job states · Command scope.

Why an accept needs vision

The engine can say the player collides with a floor while the player is drawn in the wrong place or is not visible. The measured verification row includes seeded visual failures; its scope is one game. Verification evidence · Pixel-observer evidence.

The current installed verify/sample path judges under the both rule: a passing engine record needs a visual pass too. No key, no cap, no answer or an unanswered question is not positive visual evidence. An engine failure can already reject. This default is tested offline; the ledger’s cited live orchestrator run predates it. Current rule, evidence and limit.

Vision is still fallible and not wholly independent: the recorded observer needs the engine’s ground line. Do not turn a model’s answer into a claim of protected capture. Observer limits · Capture limits.

Evidence grade is separate from capability status

The ledger’s status asks how far a mode is proven: implemented, integrated, measured or experimental. A measured mode is not automatically a release-grade guarantee. Status definitions.

GradeMeaning and current limit
fixtureSaved or synthetic inputs. Never clears a release.
diagnosticA real engine/browser run or live model answer, with declared isolation. Does not clear a release.
isolatedRequires sandboxed replay without network, checks from the base and a separate trusted job that judges and signs. No ledger row has this grade.
protectedAlso requires capture the game cannot forge. Reserved; the check refuses this grade.

An accept is not release clearance or a trusted receipt

Read the decision, evidence grade, policy and stated limits together. No current ledger row reaches isolated or protected grade. A diagnostic accept should not be promoted to release clearance just because a command exited zero. Missing trusted-judgment boundary · Signing scope.

A signature can bind a payload’s bytes to a key; it cannot prove the capture was honest or the checks were sufficient. The historical signing path uses a key generated per run. The ledger records no offline trust store or verifier receipt, and the installed trust-check command is not built. Do not describe its output as a trusted receipt. Signing evidence and missing receipt · Installed-command limits.

The threat model has an important open boundary

  • Untrusted candidate code. A change may deliberately alter behavior, evade checks or forge the frames and trace it writes. The harness’s capture is game-originated. Capture boundary.
  • Limited containment. The measured replay sandbox is for the listed Godot/Linux path. It shares the host kernel and is not a virtual machine; its resource and platform limits are in the row. Sandbox boundary.
  • Trusted policy still needs judgment. Base checks and routes keep candidate edits from quietly replacing the policy, but incomplete checks cannot prove untested behavior. Policy boundary · Coverage limits.
  • Missing evidence is not permission. Observer outages and absent settings can leave needs-review. Current vision-default tests are offline, not a newly measured live default. Observer-failure scope.
  • Small measured scope. Results on seeded changes in the bundled game are not a catch rate for another game or proof against every malicious change. Measured scope.
